| HIGH | `src/sandbox/landlock.rs:44-69` | `availability()` probes capabilities most-inclusive-first, which makes both fallback branches unreachable and rejects the kernels the branch claims to support. `supports(write_rights())` demands the *whole* `AccessFs::from_write(ABI::V4)` set (which includes `Refer` **and** `Truncate`) under `CompatLevel::HardRequirement`; per `landlock-0.4.7` `src/compat.rs:855-873`, a partially-supported set under `HardRequirement` returns `Err`. So the first check fails on any kernel below ABI 3 (Linux 6.2). Consequences: (a) the `Degraded`/TRUNCATE branch at lines 61-68 is dead code; (b) the ABI-1/`Refer` branch at lines 53-60 is dead code; (c) on an ABI-2 kernel (Linux 5.19-6.1 — Debian 12, Amazon Linux 2023's default 6.1) `select("auto")` returns `Unavailable`, so `wtclaude` **refuses to launch at all**, directly contradicting `README.md` ("Linux 5.19+", "Linux 6.2+ is preferable ... warns once") and `docs/adr/0001` ("Landlock ABI 2 (kernel 5.19) is the floor"); (d) on ABI 1 (Ubuntu 22.04's 5.15, RHEL 9's 5.14) the user gets the wrong diagnostic ("no usable Landlock support ... needs Linux 5.13+ ... check CONFIG_SECURITY_LANDLOCK") instead of the accurate REFER explanation. No test covers this because the only availability test (`landlock.rs:280`) runs on the CI/dev kernel, which is ABI 5+. | Probe least-capable-first: `supports(AccessFs::from_write(ABI::V1))` for "Landlock at all" → `supports(AccessFs::Refer)` for the ABI-2 floor → `supports(AccessFs::Truncate)` for the `Degraded` caveat. `restrict()` can keep requesting the V4 set under the default `BestEffort`, which already downgrades correctly. Consider a unit test that asserts the three messages are selected for a stubbed capability triple, so the branches stop being untestable. |
| HIGH | `src/sandbox/landlock.rs:113-126`, `src/sandbox/mod.rs:97` | On Linux the sandbox wrapper *is* the `wtclaude` binary (`confine` re-execs `std::env::current_exe()`), and `$HOME/.cargo` is a granted write subtree (`PKG_CACHE_DIRS`). Verified on this host: inside a live ruleset, `echo x > ~/.cargo/bin/wtclaude-probe` succeeds. `cargo install --path .` is the standard way to get `wtclaude` onto `PATH` at `~/.cargo/bin/wtclaude`, and dogfooding from `./target/debug/wtclaude` puts it inside the sandbox root itself. A session can therefore overwrite the binary that applies the ruleset; the next Bash call execs attacker/agent-controlled code with no restrictions at all. This is the same hazard the `SessionDir` doc comment (`mod.rs:341-348`) explicitly designs around for profile files ("`/tmp` is writable by the session, so a profile kept there could be rewritten by the session it constrains") — the reasoning was not extended to the wrapper binary. Note the hook-binary half of this (settings.json `command` is also `current_exe`) pre-exists on `main` for both platforms; the *wrapper* half is new and Linux-specific, and `README.md`'s installation section (`/usr/local/bin`) is not the path most users take. | At minimum, refuse to launch (or warn loudly) when `current_exe()` resolves inside any granted `write_subtrees` entry; better, exclude the directory holding `current_exe()` from the plan the way the session dir is excluded. If the residual risk is accepted, say so explicitly in ADR-0001 rather than leaving the `SessionDir` comment implying the opposite. |
| HIGH | `src/launch.rs:1088` (reached from `src/sandbox/mod.rs:237`), `src/sandbox/mod.rs:97` | Sharper variant of the row above, with a different mechanism and a different fix. `plan()` → `git_dirs()` runs `Command::new("git")`, i.e. a **`PATH` lookup**, and this branch makes that spawn happen on *every* Bash call (previously once at launch) from two places that are both unconfined at that moment: the PreToolUse hook process is never sandboxed, and inside `wtclaude sandbox` the spawn happens *before* `restrict(&plan)` is applied. Because `PKG_CACHE_DIRS` grants `$HOME/.cargo` and `~/.cargo/bin` is first on `PATH` in a standard rustup setup (verified on this host), a session can plant `~/.cargo/bin/git` and get arbitrary **unconfined** execution on the next Bash call — no need to overwrite the `wtclaude` binary itself. | Resolve `git` to an absolute path once at launch and thread it down, so the per-call derivation performs no `PATH` lookup. Better still, have the hook pass the plan it already computed to the wrapper via argv (which the hook controls) instead of making the wrapper re-derive it — that removes the pre-`restrict` spawn entirely and also fixes the duplicated-work finding below. |
| MEDIUM | `src/sandbox/mod.rs:352-382` (also `README.md` "Sandboxes nest on Linux", `docs/adr/0001-sandbox-backends-behind-a-trait.md`) | The claim that "a `wtclaude` session inside a `wtclaude` session works" holds only for the bare `wtclaude sandbox` wrapper (what `tests/sandbox_linux.rs:204` and `:233` exercise), not for a real nested launch. `SessionDir::base()` puts the scratch dir under `$HOME/.local/state/wtclaude/sessions`, deliberately outside the plan, so `SandboxSession::start` → `SessionDir::create` → `create_dir_all` fails. Verified: `mkdir -p ~/.local/state/wtclaude/sessions/probe` inside a live ruleset returns `Permission denied`. Landlock never uses the session dir for anything but a liveness check (`landlock.rs:114-119`), so requiring it is precisely what breaks the advertised nesting. | Either narrow the README/ADR wording to "Landlock rulesets stack, so the wrapper nests and cannot widen the outer grant", or let a backend that materializes nothing tolerate an absent session dir (e.g. make the liveness proof a backend-declared requirement) and add an integration test for a genuinely nested `wtclaude path` launch. |
| MEDIUM | `src/hook.rs:176-186`, `src/sandbox/landlock.rs:110-113` | On Linux the plan is computed twice per Bash call and the first copy is thrown away. The hook calls `sandbox::plan()` (which loads+validates `wtclaude.yml`, spawns `git rev-parse --git-dir --git-common-dir`, and canonicalizes ~20 paths), hands it to `Landlock::confine`, whose signature is `_plan: &Plan` — ignored by design, because `wtclaude sandbox` re-derives it. So every Bash call pays two `git` spawns, two YAML loads and two canonicalization passes where one would do. The hook-side call does still serve as a fail-closed config check, but that is a much cheaper question than a full plan. | Add a `Backend` method (e.g. `fn needs_plan(&self) -> bool`, or make `confine` take `&dyn Fn() -> Result<Plan>`) so the hook derives the plan lazily only for backends that consume it; keep an explicit `config::load_user()` call for the fail-closed validation. |
